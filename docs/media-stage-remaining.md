## 0. เกต "ทรงเตี้ย" พลาดมือถือรุ่นใหม่ไป 0px — ขยับเป็น 480px แล้ว

`stage.css` นิยามทรงเตี้ยไว้ที่ `aspect-ratio >= 0.9 and height < 440px` ซึ่งเขียนตอนที่
เครื่องอ้างอิงคือ 844×390 **iPhone 16 Pro Max แนวนอนสูง 440 พอดี** พอกดเต็มจอ เวทีเป็น 956×440
แล้ว `440 < 440` เป็นเท็จ → ทุกเกมหลุดไปใช้ทรงกว้าง (เดสก์ท็อป) บนมือถือ

วัดที่ family-tree เทียบสองเครื่องที่ต่างกัน 10px:

| เวทีเต็มจอ | เข้าเกต | การ์ดโจทย์ | คลังคำ | ต้นไม้ |
|---|---|---|---|---|
| 932×430 | ✅ | 47px | 33px | scale **0.66** |
| 956×440 | ❌ | 87px | 101px | scale **0.27** |

**จังหวะที่โดนคือตอนกดเต็มจอ** — ไม่เต็มจอ แถบ URL กิน 44–60px เวทีเลยต่ำกว่า 440 เข้าเกตปกติ
พอครูกดเต็มจอเพื่อฉายให้เด็กดู เวทีเต็ม 440 แล้วหลุด คือโดนตอนใช้งานสำคัญที่สุด

### แก้ 45 จุด ไม่ใช่ 44

`height < 440px` เขียนตายตัวใน 16 เกม + `stage.css` และ **1 จุดอยู่ใน `<style jsx>` ของไฟล์ `.tsx`**
(coding-maze — ดู contract ข้อ 5) การค้นด้วย `--include=*.css` อย่างเดียวจึงพลาดจุดนั้น
และเป็นจุดที่ทำให้ intro ของเกมนั้นหลุดเวที 70px · บวก `motion-lab` ที่มีแถบ
`(height >= 440px) and (height < 580px)` ซึ่งต้องเลื่อนขอบล่างตามไปเป็น 480 ไม่งั้นเกิดช่องโหว่ 440–480

ไม่แตะ 2 จุดที่เป็นเลข 440 แต่ไม่ใช่ gate — `max-width: 440px` ของ sound-wheel
กับ `min(76%,440px)` ที่เป็นความกว้างเขาวงกตของ coding-maze

### เพิ่ม `956x440` เข้าซูท เพราะไม่มีอะไรทดสอบมันได้เลย

ความสูงเวทีของ 6 ขนาดเดิมคือ 304, 343, 390, 396, 540, 617, 768, 800, 812, 1024, 1080
— **ไม่มีตัวไหนอยู่ในช่วง 440–480** ซูทจึงมองไม่เห็นทั้งบั๊กเดิมและการแก้ ผลจะออกมาเท่าเดิมเป๊ะ
ซึ่งดูเหมือนข่าวดีแต่แปลว่ายังไม่ได้ทดสอบ (ดูข้อ 3.7 เรื่องผลว่างที่พิสูจน์ไม่ได้)

ซูทโตเป็น 840 ช่อง เวลารันประมาณ 48 นาที

### ช่องใหม่เจอ hard fail ทันที 3 แถว — และพิสูจน์แล้วว่าเป็นของเดิม

```
coding-maze / intro / 956x440 / fullscreen   ปุ่ม "เริ่มภารกิจ"        หลุด 70px
motion-lab  / intro / 956x440 / in-page      ปุ่ม "เข้าสู่ห้องทดลอง"   หลุด  2px
motion-lab  / lab   / 956x440 / in-page      ปุ่ม "โจทย์จากการทดลอง"  หลุด  4px
```

**two-way test:** ถอยเกตกลับเป็น 440 โดยคงขนาดใหม่ไว้ในซูท แล้วรันซ้ำ — **ตกเหมือนกันทั้งสามแถว**
แปลว่าการขยับเกตเป็นตัวเปิดโปง ไม่ใช่ตัวก่อ · เหตุผลตรงกับที่วัดได้: motion-lab สองแถวเป็น in-page
ซึ่งเวทีคือ 892×343 ต่ำกว่า 440 อยู่แล้ว เกตไม่เคยเกี่ยวด้วยเลย

และยืนยันอีกทางว่าเกตไม่กระทบช่องเดิม: `vocabulary-arcade` ซึ่งไม่ได้ถูกแตะเลย ให้
`belowComfortTargets` = **596 เท่ากันเป๊ะ** ทั้งเกต 440 และ 480 บน 6 ขนาดเดิม

### สาเหตุจริงของทั้งสาม — คนละอย่างกับที่เดาไว้ทั้งคู่

- **coding-maze** — ไม่ใช่เรื่องขนาด แต่บล็อกทรงเตี้ยไม่ทำงานเพราะ gate ที่ตกหล่นใน `.tsx`
  แก้แล้ว overflow 70px → **−117px**
- **motion-lab** — เดาว่าเป็น specificity ตามที่ข้อ 8.5 เคยบันทึก **แต่วัดแล้วผิด**
  ยิง `outline-width` ที่ (0,1,1) เข้าไปแล้วค่าเปลี่ยน = query match และ selector ชนะ
  สาเหตุจริงคือกฎฐาน `.primary,.runButton{padding:13px 28px !important}` ทับบล็อกทรงเตี้ยที่ไม่มี
  `!important` ปุ่มเลยสูง 56px แทน 44px — **12px บนหน้าจอที่ขาด 2px** (เพิ่มเข้า contract แล้ว)
  ส่วนหน้า lab ยุบระยะคอลัมน์ควบคุมได้คืน 21px ตามลำดับของ contract ข้อ 7 ไม่ได้ตัดอะไรทิ้ง

### ข้อ 3 คือบั๊กที่รุนแรงที่สุดของทั้งเฟส และเกือบหลุดไป

`.cardArea` เป็น flex `align-items:center` + `overflow:visible` การ์ดคำถามสูง 189px แต่พื้นที่ได้ 46px
ส่วนเกิน 66px ไปนั่งทับแถวปุ่มที่สูง 64px = **ปุ่ม IS/ARE ถูกคลุมมิด กดไม่ได้เลย** (คลิก 12 ครั้ง progress ค้าง 1/12)

การ์ดสูง 189px เพราะทุกมิติวัดจาก **`cqi` (ความกว้าง)** บนเวทีที่กว้าง 780px แต่เตี้ย 304px —
กับดักที่ contract เขียนเตือนไว้ ตัวเดียวกับที่เจอในหัวเรื่อง intro ของ motion-lab

**ไม่มี check ไหนในระบบเห็นได้** — ปุ่มอยู่ในเวที ไม่ถูก clip ขนาดเต็ม ผ่านทุกเกณฑ์ที่มี แค่ถูกทับ

> **ช่องว่างที่ยังอยู่:** audit ยังไม่มี check สำหรับ "control ถูก element อื่นทับ"
> ตอนนี้พึ่งการที่ `clickFirst` ไม่ใช้ force แล้ว Playwright จะฟ้องพร้อมชื่อ element ที่ขวาง —
> แต่ครอบเฉพาะเกมที่มี walk เท่านั้น เกมที่ไม่มี walk ยังตรวจไม่ได้

### ลองเขียน check ตัวนี้แล้ว — รอบนั้นใช้ไม่ได้ (ปิดแล้วที่ข้อ 3.7)

แนวคิดตรงไปตรงมาคือยิง `elementFromPoint` ที่จุดกึ่งกลางทุกปุ่ม แล้วดูว่าได้ปุ่มนั้นกลับมาไหม
**เขียนแล้ว ทดสอบแล้ว ใช้ไม่ได้** — บันทึกไว้เพื่อไม่ให้รอบหน้าเสียเวลาซ้ำ:

1. รอบแรกได้ **312 แถว** ซึ่ง **85% เป็น modal บังปุ่มข้างหลัง** = พฤติกรรมที่ถูกต้อง ไม่ใช่บั๊ก
2. ใส่ตัวกรอง 3 ชั้น (modal / ปุ่มนอกเวที / `NEXTJS-PORTAL` ของ dev server) เหลือ **35 แถว**
3. **ตัวกรอง modal กินบั๊กจริงทิ้งด้วย** — `.kc-stage-body` เป็น `position:absolute; inset:0`
   อยู่แล้วโดยนิยาม ทุก element เลยเข้าเงื่อนไข "อยู่หลัง modal" check เงียบทั้งระบบ
   (จับได้เพราะทดสอบ 2 ทิศทาง: ของที่แก้แล้วต้องเงียบ **และ** ของที่ใส่บั๊กกลับต้องดัง)
4. แก้ตัวกรองแล้วรันจริง — **35 แถวที่เหลือ ไม่มีอันไหนเป็นบั๊กจริงเลยสักอัน**
   ทดสอบด้วยการกดจริงทั้ง density-lab, talk-card, math-bomb — กดติดหมดทุกตัว

**สาเหตุที่ล้มเหลว:** harness รีเซ็ต `scrollTop` ทุก element เป็น 0 ก่อนวัด (จำเป็นสำหรับ check อื่น
ทั้งหมด — ดู contract §6) แต่ผู้ใช้จริง**เลื่อนไปหาปุ่มที่จะกด** วัดที่ density-lab ได้ชัด:

```
ที่ audit วัด        : slider y=624 → elementFromPoint ได้ tankArea
หลัง scrollIntoView  : slider y=593 → ได้ INPUT ถูกตัว
```

"ถูกทับที่ scroll 0" ≠ "กดไม่ได้" — ส่วน is-are-sorting ต่างออกไปจริงๆ เพราะการ์ดทับปุ่มโดยไม่เกี่ยวกับ
scroll เลย (Playwright เลื่อนให้แล้วยังปฏิเสธ)

**ถ้าจะทำให้ถูก** ต้องเลื่อน control เข้ามาในจอก่อนแล้วค่อย hit-test ซึ่งขัดกับการรีเซ็ต scroll ที่ check
อื่นต้องพึ่ง — แปลว่าต้องแยกเป็น pass ต่างหาก ไม่ใช่ยัดเข้าไปใน `auditStage()`

## 6. จอสรุปของ science-lab-crisis — ปิดแล้ว ตัดสินใจว่าไม่แก้

`ScienceLabGame.tsx` เคยเขียน ``className={`${styles.result} ${styles.final}`}`` แต่ CSS module
ไม่มีคลาส `.final` การ์ดจึงออกเป็น `class="...__result undefined"` — คำว่า `undefined`
หลุดเป็นชื่อคลาสจริงใน production **แก้แล้วที่ `4b68a4b`** โดยลบ reference ที่ไม่มีปลายทาง
ไม่ได้แต่งคลาสขึ้นใหม่ หน้าตาไม่เปลี่ยนแม้แต่พิกเซลเดียว

### เรื่อง accent — ตัดสินใจแล้วว่าคงสีกลางไว้

เดิมค้างไว้ว่า `.result` เป็นฐาน `.success`/`.fail` เป็น accent จอสรุปจึงเป็นตัวเดียวที่ไม่มี accent
**ไล่ดูโค้ดแล้วพบว่านั่นคือการเลือกที่ถูกอยู่แล้ว ไม่ใช่ช่องว่าง**

การ์ดสรุปใบเดียวกันถูกใช้ทั้งสองกรณี:

| สถานะ | หัวข้อ |
|---|---|
| `complete` | 🏆 ALL SYSTEMS SECURED · ภารกิจห้องทดลองเสร็จสมบูรณ์! |
| `gameover` | 🚨 LAB SHUTDOWN · พลังชีวิตหมด |

ส่วนการ์ดรอบย่อยมีสีจริง — ชนะเป็นเขียว (`.success`) แพ้เป็นชมพู (`.fail`) ยืนยันจากภาพ audit

ถ้าใส่สีให้การ์ดสรุป สีเขียวจะผิดตอน "พลังชีวิตหมด" สีแดงจะผิดตอนชนะ
**สีกลางคือคำตอบที่ถูกสำหรับการ์ดที่ต้องรับใช้ทั้งสองปลายทาง** — ซึ่งเป็นเหตุผลเดียวกับที่
math-bomb เลือกสีทองกลาง ๆ ให้ `.finalCard` ของมัน ไม่ใช่เพราะลอกกัน

ปุ่มหลักบนการ์ดมี accent ทองอยู่แล้ว และมีถ้วยรางวัลนำ จึงอ่านออกว่าเป็นการฉลองโดยไม่ต้องย้อมทั้งใบ

**สรุป: ไม่แก้ ไม่ใช่งานค้าง**

## 7. accessibility — แก้แล้วทั้งสองจุด และเอกสารเดิมเข้าใจผิดไปหนึ่งข้อ

| เกม | commit | ผล |
|---|---|---|
| sound-wheel | `cec0855` | `nonSemanticControls` 12 → 0 |
| digital-sort | `46ebd3f` | คงไว้ 12 โดยตั้งใจ (เหตุผลข้างล่าง) |

### sound-wheel — canvas เป็นทางลัดซ้ำ

`<canvas onClick={spin}>` เรียก `spin()` ตัวเดียวกับปุ่ม `หมุนวงล้อ!` ที่อยู่ใต้มันพอดี
ปุ่มนั้นห่างแค่ **1 tab** และหมุนได้จริงจากคีย์บอร์ด (ทดสอบด้วยการกดจริง ไม่ได้อ่านโค้ดเอา)
ตัวอักษรบนวงล้อวาดลงใน bitmap — ต่อให้ screen reader หยุดตรงนั้นก็ไม่มีอะไรให้อ่าน
มีแต่จะได้ทางเข้าที่สองที่ไม่มีชื่อ ไปยังสิ่งที่ control ถัดไปทำอยู่แล้ว

`aria-hidden="true"` จึงเป็นการติดป้ายที่ตรงความจริง และวงล้อยังคลิกด้วยเมาส์ได้เหมือนเดิม

### ของที่ใหญ่กว่าและไม่มี check ไหนเคยรายงาน: ทั้งสองเกมไม่มี live region เลย

- **sound-wheel** — ผลที่หมุนได้ ซึ่งเป็นทั้งหมดของหน้าจอ ปรากฏขึ้นเงียบ ๆ
  ตอนนี้เป็น `role="status"` ยืนยันแล้วว่าประกาศ "พยัญชนะต้น a–z / b / ตัวอย่างคำ…" หลังหมุน
- **digital-sort** — การ์ด**คือโจทย์** และมันเปลี่ยนทุกครั้งที่ตอบ
  คนใช้ screen reader ตอบข้อหนึ่งแล้วไม่เคยรู้เลยว่าข้อถัดไปคืออะไร
  ตอนนี้การ์ดกับ feedback เป็น live region ยืนยันแล้วว่าประกาศข้อถัดไปทันทีหลังตอบ

### เอกสารเดิมเข้าใจผิดเรื่อง digital-sort

เดิมเขียนว่า "เป็น drag source ต้องการทางเข้าถึงด้วยคีย์บอร์ด" — **ไม่จริง**
บิน "ฮาร์ดแวร์" กับ "ซอฟต์แวร์" เป็น `<button onClick={sort(...)}>` จริง
**เล่นจบทั้งเกมด้วย Tab กับ Enter ล้วนได้** (ทดสอบแล้ว 12 ข้อ ถึงหน้าจบ)
การลากการ์ดเป็นทางเลือกเสริม ไม่ใช่ทางเดียว

ผลพลอยได้: การ์ดมีข้อความ "⋮⋮ ลากการ์ดไปยังคำตอบ" อยู่ข้างใน พอทำเป็น live region แล้ว
มันจะถูกอ่านทุกครั้งที่ตอบ ให้คนที่ทำตามไม่ได้ จึงใส่ `aria-hidden` ให้ข้อความนั้น

### ทำไมยังคง 12 แถวของ digital-sort ไว้

การ์ดลากยังขึ้นใน `nonSemanticControls` และ**ตั้งใจปล่อยไว้**

ใส่ `role="button"` จะทำให้ check เงียบ แต่เป็นการอธิบายมันว่าเป็นสิ่งที่มันไม่ใช่
ส่วน role อื่นที่ตรงความจริงกว่า check ก็ยังฟ้องอยู่ดี (ตัวกรองรับเฉพาะ
`button/a/input/[role=button|link|checkbox|radio|tab|option]`)

เหตุผลที่รับได้ควรอยู่ในเอกสาร ไม่ใช่ใน attribute ที่ผิด — WCAG 2.1.1 ถามว่า
"ทำสิ่งนี้ด้วยคีย์บอร์ดได้ไหม" คำตอบคือได้ ผ่านบินที่เป็นปุ่มจริง

### เรื่องที่เจอระหว่างทาง ยังไม่ได้แก้

กว่าจะ tab ถึงปุ่มเริ่มเกมใช้ **27–35 ครั้ง** เพราะต้องผ่าน navigation ของเว็บทั้งหมดก่อน
เป็นความหนืดจริงสำหรับคนใช้คีย์บอร์ด แต่อยู่นอกขอบเขตของ stage contract
(เป็นเรื่องของ layout หลัก ไม่ใช่ของเวทีเกม) — ยังไม่ได้แตะ ควรมี skip link

## 8. ข้อจำกัดที่ยังอยู่ (รู้ตัว ไม่ใช่ลืม)

### วัดจาก headless viewport ตายตัว

`dvh` บนมือถือจริงขยับตามแถบ URL ที่ซ่อน/โผล่ เวทีจริงจึงอาจสูงกว่าที่วัดได้เล็กน้อย
เคสที่คับที่สุดตอนนี้คือ family-tree `plant-tree` (เป้าแตะ 26px) กับ matching (25px)
ทั้งคู่เหลือ margin เหนือเกณฑ์ 24px แค่ 1–2px — **ควรลองบนเครื่องจริงสักรอบ** (ยังไม่ได้ลอง)

### harness ยังพึ่ง sleep คงที่

ทุกจังหวะรอใช้ `waitForTimeout` ค่าคงที่ ไม่ได้รอเงื่อนไขจริง — warmup ของ sound-wheel อย่างเดียว
นอน 5400ms × 12 = 65 วิต่อขนาด และเคยวัดพลาดมาแล้วครั้งหนึ่ง (วัดตอน explode keyframe ยังไม่จบ
ทำให้การ์ดพองไป 45% ต้องขยับเป็น 2500ms) เปลี่ยนไปรอเงื่อนไข (`toBeVisible`) จะเร็วกว่าและ
ตัดบั๊กประเภทนี้ทิ้งทั้งกลุ่ม แทนที่จะไล่จูนค่าคงที่ทีละครั้งที่โดน

### จุดเปราะใน harness ที่รายงานไว้แต่ยังไม่แก้

- solver ของ math-bomb `won` ใช้ `eq.match(...)` โดยไม่เช็ค null — สมการที่ไม่ใช่รูป `NN op NN`
  (en dash, 3 พจน์, มีวงเล็บ) จะ throw ตอนนี้ blast radius ถูกจำกัดด้วย try/catch แล้วแต่ walk ยังพัง
- `page.locator("button", { hasText: "ตั้งค่า" })` เป็น substring match — ถ้ามีปุ่มที่สองที่มีคำนี้
  จะ throw strict-mode (math-bomb มี `ตั้งค่าภารกิจ` กับ `ตั้งค่าใหม่` อยู่แล้ว)
- `[class*="__mission"]` ก็ match `__missionMeta` ด้วย — วันไหนมี `strong` ในนั้นจะ throw

### เกมที่ยังไม่ได้ตรวจบางหน้าจอ

- `typing-defense` ยังมีหน้า `levelIntro` ที่เข้าได้เฉพาะโหมด adventure หลังเล่นจบรอบหนึ่ง — ยังไม่อยู่ใน config
- กลุ่ม C: `classroom-objects` กับ `vocabulary-arcade` **ปิดแล้ว** (ดูข้อ 3.5) เหลือ `typing-defense`
  หน้าเล่นจริง/หน้าจบ, `family-tree` stage 5, `phonics-bingo` — สามตัวนี้แพงกว่ากันหลายเท่า
- `sound-wheel`/`law-daily` ไม่มีหน้าผลลัพธ์โดยธรรมชาติของเกม (กลุ่ม D เดิม) — ไม่ต้องทำอะไรเพิ่ม

### phonics-bingo — ไอเดียที่ยังไม่ได้ลอง

เคยตัดออกเพราะคิดว่าทำอัตโนมัติไม่ได้ (ต้องฟังเสียงแล้วแตะให้ตรง) **แต่ยังไม่ได้ลองจริง**
เกมมีปุ่ม `👀 ครูดูเฉลย` ที่บอกว่าช่องไหนถูก — แนวทาง: กดดูเฉลย อ่าน DOM ว่าช่องไหนถูกทำเครื่องหมาย
แตะช่องนั้น กด `🔊 ฟังอีกครั้ง` ทำซ้ำจนบิงโกครบแถว ยังไม่ได้ลองว่าใช้ได้จริงหรือไม่

กฎฐาน `.introCopy>p:not(.eyebrow){margin:18px 0}` = specificity **(0,2,1)**
กฎบีบในบล็อกจอเตี้ยเขียน `.introCopy>p{...}` = **(0,1,1)** จึงแพ้
**กฎบีบ intro บนจอเตี้ยไม่เคยทำงานเลย** บล็อกแนวตั้งบังเอิญเขียน selector ถูกจึงทำงาน

audit เดิมจับไม่ได้เพราะ**มันวัดกล่อง ไม่ได้วัดว่ากฎที่เขียนถูกใช้จริงไหม** และหน้าจอก็ผ่าน
ทุกขนาดในซูท — ผ่านด้วยระยะ 1px แก้ specificity ให้ตรงกัน = 8px → 48px

ตระกูลเดียวกับ `2cc843a` — กฎที่อ่านแล้วดูถูกแต่ไม่ทำงาน อันนั้นแพ้เพราะลำดับ อันนี้แพ้เพราะ specificity

### phonics-bingo หน้าจบ — เข้าถึงได้แล้ว (`6062e70`) และเจอบั๊กทันที (`ad8ce0c`)

เคยตัดออกเพราะคิดว่าต้องฟังเสียง **ปุ่ม `👀 ครูดูเฉลย` ของเกมเองคือทางเข้า** — เปิดแล้ว
เสียงที่เรียกจะแสดงเป็น `/xx/` ให้อ่านได้ตรง ๆ กดช่องที่ตรงแล้วเกมเลื่อนไปเสียงถัดไป
ต้องทำครบทุกช่อง ไม่ใช่แถวเดียว — วัดได้ 16 ช่องใน 19 taps + 4 skips

สองอย่างที่ต้องรู้ (เขียนไว้ในโค้ดแล้ว):

- ช่องที่ทำแล้วดูจาก**สีขอบ ไม่ใช่โครงสร้าง** — ทุกช่องมีลูก 3 ตัวเท่ากันไม่ว่าทำแล้วหรือยัง
  ถ้าเช็คโครงสร้างจะได้ว่าครบทั้งกระดานตั้งแต่เฟรมแรก
- เสียงที่เรียกบางทีไม่มีบนกระดาน หรือทำไปแล้ว และ**ไม่มีปุ่มข้าม** —
  กดช่องที่ยังว่างช่องไหนก็ได้คือสิ่งที่ทำให้เกมเลื่อนไป

**บั๊กที่เจอ**: ที่ 844×390 กองเนื้อหา 415px ในกล่อง 236px **ปุ่ม "เล่นอีกครั้ง" กับ
"ตั้งค่าใหม่" อยู่นอกจอทั้งคู่** (2/2, ซ่อน 201px) เล่นจบแล้วมองไม่เห็นว่าจะเริ่มใหม่ยังไง
ที่ 768×1024 ก็ซ่อนเหมือนกัน บีบถ้วยกับดาวเหลือ 260px ปุ่มกลับเข้าจอครบ

### skip link (`d82644d`)

วัดตอนตรวจ accessibility: กว่าจะ tab ถึงปุ่มเริ่มเกมใช้ **28 ครั้ง** (motion-lab)
และ **36 ครั้ง** (sound-wheel) เพราะต้องผ่าน header ทั้งหมดก่อน ใส่ skip link แล้วเหลือ 8 กับ 16

เลือกวิธี anchor เปล่าหลัง Header แทนการใส่ `id` ที่ `<main>` ของแต่ละหน้า เพราะ
48 จาก 65 หน้ามี `<main>` อีก 17 ไม่มี — ทาง id ต้องแก้ 48 ไฟล์แล้วยังเหลือหน้าที่ skip link เสีย
และหน้าเกม render `<main class="flex-1">` เป็นลูกตรงของ `<body>` ครอบ div จะทำให้ `flex-1` พัง
ส่วน flex item ขนาด 1280×0 ไม่กระทบอะไร ยืนยันแล้วด้วย audit 3 เกม ทุก check ไม่ขยับ
