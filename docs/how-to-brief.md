# วิธีสั่งงานเซสชันใหม่

ไฟล์นี้มีบรีฟสำเร็จรูป 2 อัน ก๊อปวางได้เลย ไม่ต้องเขียนใหม่ทุกครั้ง

เซสชันใหม่ไม่รู้อะไรเลยเกี่ยวกับรอบก่อน — รู้แค่สิ่งที่อยู่ในไฟล์ บรีฟพวกนี้จึงมีหน้าที่
ชี้ไปที่เอกสารที่ถูกต้อง และ**ดักความผิดพลาดที่เคยเกิดจริง** ไม่ใช่แค่บอกว่าจะทำอะไร

ไม่ผูกกับผู้ช่วยเจ้าไหนเป็นพิเศษ — ใช้กับ agent ตัวไหนก็ได้ที่ทำครบ 3 ข้อข้างล่าง

---

## เงื่อนไขของ agent — เช็คก่อนเริ่ม

### 1. ต้องเปิดดูไฟล์ PNG ที่ตัวเองสร้างได้

ข้อนี้สำคัญที่สุด งานรีวิวสัดส่วนทั้งหมด**ตัดสินด้วยตา ไม่ใช่ด้วยตัวเลข** —
`audit-games.mjs` วัดเงื่อนไขความพัง ไม่มี check ตัวไหนวัดความสมดุล
เกมที่เนื้อหากองมุมเดียวแล้วเหลือที่ว่าง 60% ผ่านเขียวสนิททุกช่อง

เคสจริง: `sound-wheel` เคยวาดวงล้อขาดหายไปสองด้าน โดย audit ขึ้นเขียวครบทุกช่อง
จับได้จาก screenshot อย่างเดียว

**วิธีเช็ค** ให้มันถ่ายภาพ 1 รูปแล้วสั่งว่า *"เปิดไฟล์นั้นแล้วบอกมาว่าเห็นอะไร"*
ถ้าบรรยายได้ตรงกับที่เห็นจริง = ใช้ได้เต็มรูปแบบ

**ถ้าเปิดภาพไม่ได้** ยังใช้ต่อได้ แต่ต้องเปลี่ยนวิธี: สั่งให้มันวัดตัวเลขกับถ่ายภาพเก็บไว้
แล้ว**คุณเปิดดูเอง** และเป็นคนตัดสินว่าสวยพอหรือยัง — อย่าให้มันสรุปเรื่องสัดส่วน
จากตัวเลขล้วน เพราะนั่นคือสิ่งที่ audit ทำอยู่แล้วและมันมองไม่เห็น

### 2. ต้องรันคำสั่งเองได้โดยไม่ติดขออนุมัติทีละบรรทัด

ต้องใช้ `node`, `npx playwright`, `git` และเขียนไฟล์ได้
`audit-games.mjs` กินเวลา 5–8 นาทีต่อเกม (ทั้งซูท ~48 นาที) ถ้าต้องกดอนุมัติทีละคำสั่ง
จะสะดุดกลางทาง — เปิดโหมดที่รันเองได้ในโฟลเดอร์นี้

### 3. ต้องกล้าค้าน

บรีฟข้างล่างมีบรรทัด *"ต้องวัดยืนยันทุกข้อก่อนจะเห็นด้วยหรือค้าน ถ้าทำซ้ำไม่ได้ให้บอกตรง ๆ"*
— บรรทัดนี้คือสิ่งที่ทำให้รอบ family-tree ได้ผล agent ค้านเจ้าของงานไป 1 ข้อ
(อาการที่ทำซ้ำไม่ได้) และเดาสาเหตุผิดเอง 2 ครั้งแล้วการวัดจับได้ทั้งคู่

ถ้า agent เออออตามทุกอย่าง ตัวเลขจะสวยแต่ของจะยังพัง

## A. รีวิวสัดส่วนเลย์เอาท์ของเกมเดิม

ใช้เมื่อเกมผ่าน audit หมดแล้ว (hard fails = 0) แต่ยัง "ดูไม่สวย" — เนื้อหากองมุมเดียว
เหลือที่ว่างครึ่งจอ ตัวหนังสือเล็กเกินบนโปรเจกเตอร์ ซึ่ง **audit มองไม่เห็นทั้งหมด**
เพราะ check ทุกตัววัดเงื่อนไขความพัง ไม่มีตัวไหนวัดความสมดุล

````
ไล่ตรวจสัดส่วนเลย์เอาท์ของ <ชื่อเกม> ใน /media  branch responsive-phase-0
npm run dev รันอยู่แล้ว

อ่าน docs/media-stage-contract.md (ข้อ 3 → Checklist → ข้อ 4.5 → ข้อ 5 → ข้อ 7)
กับ docs/media-stage-remaining.md ให้จบก่อน แล้วสรุปให้ผมฟังว่าเข้าใจอะไร
ยังไม่ต้องแก้อะไรทั้งนั้น

จากนั้นวัดเกมนี้ทุกหน้าจอ × 7 ขนาด × 2 โหมด แล้วรายงานเป็นตารางมาก่อน:
ขนาดเวทีจริง (กว้าง×สูง) · %W และ %H ที่เนื้อหาใช้จริง · ตัวอักษรเล็กสุด ·
มีอะไรอยู่หลังสกรอลล์ไหม · อะไรไม่อยู่กึ่งกลาง

วิธีทำงาน:
- ผมจะไล่ดูทีละหน้าจอเองแล้วบอกสิ่งที่เจอ คุณต้องวัดยืนยันทุกข้อก่อนจะเห็นด้วย
  หรือค้าน ถ้าทำซ้ำไม่ได้ให้บอกตรง ๆ ว่าทำซ้ำไม่ได้ อย่าเออออตาม
- แก้เสร็จให้วัดด้วย probe Playwright สั้น ๆ (ใช้เวลาวินาที) ส่งตัวเลขกับภาพมาก่อน
  แล้วรอผมตรวจ อย่าเพิ่งรัน audit-games.mjs
- ผมโอเคแล้วค่อยรัน audit เกมนั้น แล้ว commit แยกทีละหน้าจอ
- ห้ามแก้ด้วย overflow:auto · ห้ามกรอง advisory เอง รายงานดิบมา
- เกมที่สุ่มเนื้อหา ทดสอบด้วยเคสยาวที่สุด ไม่ใช่ที่ seed ให้มา
````

### ทำไมต้องมีบรรทัด "วัดขนาดเวทีจริงก่อน"

รอบ family-tree ตั้ง gate ไว้ที่ `min-width: 1150px` โดยไม่ได้วัดก่อนว่าเวทีตอนไม่เต็มจอ
กว้างเท่าไร — คำตอบคือ **1096px** พลาดไป 54px ทุกกฎที่เพิ่มเข้าไปจึงไม่ทำงานเลยบน
"เดสก์ท็อปแบบไม่กดเต็มจอ" ซึ่งเป็นวิธีที่คนเปิดเกมบ่อยที่สุด กว่าจะรู้ก็ต่อเมื่อไล่ดูด้วยตา

`.kc-stage` เป็น `width:100%; aspect-ratio:16/9` เวทีในหน้าจึงกว้างเท่าคอลัมน์เนื้อหา
ไม่ว่าจอจะ 1280 หรือ 1920 — **ขนาด viewport ไม่ใช่ขนาดเวที** และ gate อ่านขนาดเวที

### ทำไมต้องรอก่อน audit

`audit-games.mjs` กินเวลา 5–8 นาทีต่อเกม และ **ห้ามแก้ไฟล์ระหว่างรัน** (dev server
hot-reload แล้ว Playwright timeout ทิ้งทั้งรอบ) ถ้าเจ้าของงานดูภาพแล้วไม่ผ่าน
รอบนั้นก็ทิ้งฟรี ให้วัดสั้น ๆ ส่งภาพ รอเคลียร์ แล้วค่อย audit ทีเดียว

### ถ้าจะแก้อะไรที่กระทบทั้งซูท

เช่นขยับ threshold ที่ใช้ร่วมกัน ต้องทำเพิ่มอีก 3 อย่าง:

1. **ค้นทั้ง `.css` และ `.tsx`** — `coding-maze` เขียนกฎ shape ใน `<style jsx>`
2. **ตรวจว่าซูทมีขนาดที่ครอบช่วงที่เปลี่ยนไหม** ถ้าไม่มีต้องเพิ่มขนาดเข้าซูท ไม่งั้น
   ผลจะออกมาเท่าเดิมเป๊ะ ซึ่งดูเหมือนข่าวดีแต่แปลว่ายังไม่ได้ทดสอบ
3. **two-way test ทุกแถวที่ตกใหม่** — ถอยการแก้ออกแล้วรันซ้ำ ถ้าตกเหมือนกัน
   แปลว่าเป็นบั๊กเดิมที่เพิ่งมองเห็น ไม่ใช่ regression ที่เพิ่งทำ

## B. สร้างสื่อ/เกมใหม่

````
จะทำเกมใหม่ใน /media
ชื่อ: <ชื่อ>   วิชา: <วิชา>   ระดับชั้น: <ป.x–ป.y>
เล่นยังไง: <อธิบายสั้น ๆ>   มีกี่ด่าน/หน้าจอ: <กี่หน้า>

อ่าน docs/media-stage-contract.md ก่อน โดยเฉพาะข้อ 1–3, Checklist, ข้อ 4.5
แล้วบอกผมก่อนเริ่มเขียนว่า เกมนี้จะมีหน้าจอไหนบ้าง และแต่ละหน้าจอ
"ทรงไหนจะเป็นตัวบีบ" (จอเตี้ยขาดความสูง / จอตั้งขาดความกว้าง)

กติกาที่ห้ามพลาด:
- ขนาดทุกอย่างอยู่ใน CSS module ห้าม inline style
- ห้ามอ่าน viewport ในโค้ดเกม (vw/vh/dvh/innerWidth/matchMedia)
- ของตกแต่งทุกชิ้นต้องมี pointer-events:none
- ใช้ useStage() กับโครงสร้าง 2 ชั้นตามข้อ 2
- ปุ่ม toolbar ใช้ .kc-tap-chrome ไม่ใช่ .kc-tap
- เสร็จแล้วเพิ่มเกมเข้า scripts/audit-games.mjs (screens / enter / expect / stress)
  แล้วรัน audit ให้ผ่านครบ 7 ขนาด × 2 โหมด ก่อนบอกว่าเสร็จ
````

### สองข้อที่แพงที่สุดถ้าพลาด

**ขนาดอยู่ใน inline style** — family-tree เขียน toolbar, hub และ intro เป็น inline
ทั้งหมด ผลคือไม่มี container query ไหนเอื้อมถึงได้เลย และ inline ชนะทุกกฎอยู่แล้ว
รอบรีวิวจึงต้องย้ายเข้า CSS module ก่อนถึงจะเริ่มแก้อะไรได้ เสียเวลาไปทั้งก้อน
เขียนถูกตั้งแต่แรกไม่มีต้นทุนเพิ่มเลย

**ไม่ได้เพิ่มเข้า `audit-games.mjs`** — เกมที่ไม่อยู่ใน config จะไม่ถูกวัดเลยจนกว่า
จะมีคนนึกได้ และสถิติในเอกสารบอกว่าหน้าจอที่เพิ่งเปิดตรวจเจอบั๊ก 5 จาก 11
และ 2 จาก 2 คือ **คาดได้เลยว่ามีของ**

### ต้องกรอกอะไรใน audit config

| ช่อง | ใส่อะไร |
|---|---|
| `path` | route ใต้ BASE_URL |
| `screens[].name` | ชื่อหน้าจอ |
| `screens[].enter` | ขั้นตอนคลิกจากหน้าก่อนหน้า (state ต่อเนื่องกันเหมือนเล่นจริง) |
| `screens[].expect` | selector ที่จะ match ก็ต่อเมื่อไปถึงจริง — **บังคับ** สำหรับหน้าที่ไปถึงด้วยการเล่น ไม่ใช่กดเมนู |
| `warmup` | ถ้าหน้าจอนั้นสูงขึ้นได้อีกหลังเล่นไปสักพัก |
| `stress` | selector + คำที่ยาวที่สุดที่เกมสร้างได้ |

ถ้าไม่ใส่ `expect` แล้ว walk เพี้ยน มันจะวัดหน้าจอผิดภายใต้ชื่อที่ถูกแล้วขึ้นเขียว

## กับดักของเครื่องมือ ไม่ใช่ของเกม

สองอันนี้เสียเวลาไปจริงในรอบ family-tree และไม่มีทางเดาได้จากอาการ

### dev server ตาย แล้วอาการออกมาเป็น 404 ทุกเกม

ถ้าจู่ ๆ ทุก route ใต้ `/media/<วิชา>/<เกม>` คืน **404** แต่ `/` กับ `/media/<วิชา>`
ยังคืน 200 — นั่นไม่ใช่โค้ดพัง แต่คือ dev server หมดแรงแล้ว compiler/watcher ตาย
มันจะ **404 ทันทีใน 0.04 วินาที ไม่พยายาม compile เลย** ซึ่งเป็นจุดที่แยกออกจาก error จริง
(error จริงจะขึ้น 500 พร้อม overlay และใช้เวลา compile ก่อน)

เกิดหลังจากแก้ CSS แล้ว hot-reload สิบกว่ารอบ + รัน audit หลายรอบ — process บวมถึง 1.3GB

**`npm run dev` ซ้ำเฉย ๆ ไม่ช่วย** เพราะตัวเก่ายังถือ port 3000 อยู่ ตัวใหม่จะ bind ไม่ได้แล้วตายเงียบ
ต้องฆ่าตัวเก่าให้ตายจริงก่อน:

```bash
netstat -ano | grep ":3000"      # เอา PID
taskkill /PID <pid> /F
npm run dev
```

**วิธียืนยันว่าฆ่าสำเร็จ** — เช็คว่า PID ที่ถือ port เปลี่ยนไปแล้ว ถ้าเป็นตัวเดิมแปลว่ายังไม่ตาย

### PostCSS ของโปรเจกต์นี้ parse container query แบบมี comma ไม่ได้

```css
/* พัง — "Unexpected token Comma" */
@container kcstage (min-width: 1150px), kcstage (aspect-ratio < 0.9) { … }
```

และมันไม่ได้แค่ตกกฎนั้น — **ทั้ง stylesheet คอมไพล์ไม่ผ่าน หน้าเว็บขึ้น 500 ทันที**
ถ้าต้องใช้เงื่อนไขสองชุด ให้เขียนแยกเป็นสองบล็อกแล้วยอมซ้ำ declaration

## เกณฑ์ที่ถือว่าเสร็จ

ไม่ใช่ "ผ่าน 12 ช่อง" แต่คือ:

- hard fails = 0 · `unreachable` / `undersizedTargets` / `smallText` = 0
- **เหลือที่ว่างอย่างน้อย 60px ที่ 844×390** (`audit-headroom.mjs`) — เพราะ browser
  จริงบนมือถือแนวนอนกินความสูงให้แถบ URL 44–60px ซึ่ง headless ไม่มี
- `contentHiddenBehindScroll` ไม่มีแถวที่ซ่อน **ปุ่มตัวเลือกหรือการ์ดคำตอบ**
  (ซ่อนท้ายย่อหน้าหรือรายการยาวปล่อยได้)
- ดูภาพจริงทุกหน้าจอ — ตัวเลขบอกไม่ได้ว่าสวยหรือยัง
