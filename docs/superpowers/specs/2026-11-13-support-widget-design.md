# กล่องรับการสนับสนุน (เลี้ยงกาแฟคุณคูล) — Design

วันที่: 2026-11-13
สถานะ: ผ่านการตรวจโดยผู้อ่านอิสระแล้ว รอเจ้าของเว็บอนุมัติก่อนเขียนแผน implement
ตัวอย่างหน้าตา: https://claude.ai/artifact/C9gJKDGX3BeACJrRjQuMys

## 1. เป้าหมาย

ช่องทางให้ครูที่ใช้เครื่องมือฟรีอยู่แล้ว ช่วยออกค่าเซิร์ฟเวอร์ได้ถ้าอยากช่วย
แนว Buy Me a Coffee แต่จ่ายด้วยพร้อมเพย์

เจ้าของเว็บบอกเป้าหมายไว้สองข้อ

1. ได้เงินก้อนเล็กๆ พอให้เว็บอยู่ต่อได้ ไม่ใช่ธุรกิจ ไม่ใช่รายได้
2. อยากรู้ว่ามีครูเห็นค่าสิ่งที่ทำอยู่บ้าง ซึ่งตัวเลขในแอปธนาคารบอกไม่ได้
   จึงต้องมีช่องให้ครูฝากข้อความ

ความสำเร็จวัดจาก "มีเงินพอจ่ายค่าเซิร์ฟเวอร์" กับ "มีครูกดจ่ายจริงสักคน"
ไม่ใช่ยอดเงิน

### ไม่อยู่ในขอบเขต (YAGNI)

- ไม่มีสมาชิกรายเดือน ไม่มีระดับผู้สนับสนุน ไม่มีสิทธิพิเศษ
- ไม่กั้นเครื่องมือหรือสื่อใดๆ ไว้หลังการจ่าย ทุกอย่างฟรีเหมือนเดิม
- ไม่มี popup เด้งขัดจังหวะระหว่างใช้เครื่องมือ
- ไม่ออกใบเสร็จ ไม่รับคืนเงิน
- ไม่ผูกกับแพลตฟอร์มต่างประเทศ (Ko-fi, Buy Me a Coffee, Stripe)
- ไม่รู้ยอดเงินอัตโนมัติ พร้อมเพย์ไม่มี webhook กลับมาที่เว็บ
  เว็บจะไม่มีวันรู้ว่าใครโอนหรือโอนเท่าไหร่

### Anti-goal

ถ้าครูรู้สึกว่า "khuncool เริ่มขอเงินแล้ว" ถือว่าล้มเหลว ต่อให้ได้เงินก็ตาม
ทุกการตัดสินใจเรื่องขนาด สี และโมชั่นในเอกสารนี้ ชั่งกับข้อนี้เสมอ

## 2. ข้อมูลที่ใช้ตัดสินใจ

ดึงจาก Search Console ช่วง 2026-10-14 ถึง 2026-11-13 (คลิกจาก Google 510 ครั้ง)

| หน้า | คลิก | สัดส่วน |
|---|---:|---:|
| `/duck-race` | 412 | 81% |
| `/group-maker` | 18 | 3.5% |
| `/tools/homeroom` | 17 | 3.3% |
| `/` (หน้าแรก) | 13 | 2.5% |
| ที่เหลือรวมกัน | 50 | 10% |

อุปกรณ์: มือถือ 230 · คอมพิวเตอร์ 219 · แท็บเล็ต 66 → **57% เป็นจอสัมผัส**

ข้อสรุปสองข้อที่ชี้นำดีไซน์ทั้งหมด

- หน้าแรกเป็นหน้าที่คนเห็นน้อยที่สุดหน้าหนึ่ง วางกล่องไว้ที่นั่นอย่างเดียว
  จะไม่มีใครเห็น จุดที่คนอยู่จริงคือท้ายหน้า `/duck-race`
- ลูกเล่น hover ไปไม่ถึงคนส่วนใหญ่ ทุกอย่างต้องทำงานได้โดยไม่ต้อง hover

ตัวเลขนี้นับเฉพาะคนที่มาจาก Google ไม่รวมคนที่กดลิงก์จากเฟซบุ๊ก ไลน์
หรือพิมพ์ชื่อเว็บเอง

## 3. แนวทางที่พิจารณา

**ก. แพลตฟอร์มต่างประเทศ (Ko-fi / Buy Me a Coffee) — ตัดทิ้ง**
เร็วที่สุด มีระบบข้อความและแจ้งเตือนพร้อม แต่ออกแบบมาสำหรับคนจ่ายด้วยบัตรเครดิต
ครูไทยส่วนใหญ่จ่ายด้วยสแกนพร้อมเพย์จากแอปธนาคาร จะได้กล่องสวยที่แทบไม่มีคนกดจ่ายจริง
บวกค่าธรรมเนียมและการถอนเงินข้ามประเทศ และคุมดีไซน์ให้เข้ากับเว็บไม่ได้

**ข. หน้า `/support` อย่างเดียว แล้วลิงก์จากฟุตเตอร์ — ตัดทิ้ง**
มี URL ให้แชร์ก็จริง แต่ตัวเลขข้างบนบอกว่าแทบไม่มีใครเดินไปถึง

**ค. แถบในหน้าที่คนอยู่ + ชีทเปิดทับ + หน้า `/support` — เลือกข้อนี้**
แถบไปปรากฏตรงที่คนอยู่จริง กดแล้วเปิดชีททับหน้าเดิมแทนที่จะพาออกไปอีกหน้า
เพราะครูอาจกำลังฉายเกมขึ้นจอหน้าห้อง การดึงออกไปอีกหน้าคือทำลายคาบเรียน
ส่วนหน้า `/support` ยังทำไว้เป็นหน้าเต็มสำหรับเอาลิงก์ไปแปะที่อื่น
ใช้คอมโพเนนต์ร่วมกับชีท เพิ่มงานอีกเล็กน้อย

## 4. แถบ (SupportStrip)

แถบเตี้ยสองบรรทัด พื้นม่วงทึบ อยู่ใต้แถวการ์ดเครื่องมือท้ายหน้า

```
┌────────────────────────────────────────────────────┐
│  ☕   เว็บนี้ฟรี เพราะมีคนช่วยค่าเซิร์ฟเวอร์     [เลี้ยงกาแฟ] │
│       เลี้ยงกาแฟคุณคูลสักแก้วไหม                     │
└────────────────────────────────────────────────────┘
       ↑ แก้วกาแฟขาว ควันลอยเป็นหัวใจล้นขึ้นเหนือขอบแถบ
```

### สเปกที่ล็อกแล้ว

| รายการ | ค่า | เหตุผล |
|---|---|---|
| พื้นหลัง | `#3F41C9` | ม่วงหลัก `#5C5EE6` สว่างเกินไป ตัวหนังสือขาวบรรทัดสองได้คอนทราสต์แค่ 3.7:1 ไม่ผ่าน WCAG AA · `#3F41C9` มีอยู่ในเว็บแล้ว (ลิงก์ข้ามไปเนื้อหา ใน `app/layout.tsx`) |
| บรรทัดหลัก | `#FFFFFF` | 5.5:1 |
| บรรทัดรอง | `rgba(255,255,255,.9)` | 4.6:1 |
| ปุ่ม | พื้นขาว ตัวหนังสือ `#3F41C9` | ปุ่มม่วงบนพื้นม่วงใช้ไม่ได้ |
| ขอบมน | `--radius-card` (16px) | เท่าการ์ดอื่น |
| แก้ว | กว้าง 76px (ภาพ SVG) | ที่ 100px แก้วเกือบเต็มความสูงแถบ อ่านเป็น "แก้วที่มีข้อความต่อท้าย" |
| ช่องไฟแก้ว–ข้อความ | ~19px | ช่องวางแก้วกว้าง 0.62 เท่าของภาพ (ตัวแก้วกว้าง 0.53 เท่า) บวก flex gap 15px |
| สูง | ~57px | ไม่เปลี่ยนเมื่อใส่ควัน ควันลอยล้นขึ้นไปข้างบน ไม่ดันแถบ |

แก้วเป็น inline SVG ไม่ใช่ไฟล์รูป จะได้ย้อมสีตามพื้นหลังได้
(แก้วขาวขอบเทา `#C3C8D6` บนพื้นม่วง) และคมทุกความละเอียด

### ตำแหน่งที่แถบไปปรากฏ

| ที่ | แบบ |
|---|---|
| `/duck-race` ใต้แถวการ์ดเครื่องมือถัดไป | แถบเต็ม |
| หน้าแรก `/` ต่อจากแถวเครื่องมือยอดนิยม (`PopularToolsSection`) | แถบเต็ม |
| `/support` | แถบเต็ม (บนสุดของหน้า) |
| ฟุตเตอร์ทุกหน้า | **ลิงก์ข้อความธรรมดา** ไม่ใช่แถบ — ดูหมายเหตุ |
| การ์ดประกาศผู้ชนะในเกม | **ไม่มี** |

**ไม่มีปุ่มปิด** เจ้าของเว็บตัดสินใจแล้วว่าแถบอยู่ตลอด ไม่ให้ครูกดซ่อน
ไม่ต้องเก็บอะไรใน localStorage และไม่ต้องมีสถานะ "เคยเห็นแล้ว"
(คนตรวจ spec ทักว่าครูเปิด `/duck-race` เกือบทุกเช้า แถบม่วงที่ปิดไม่ได้
อาจกลายเป็นแบนเนอร์ประจำเว็บแบบที่เราตัดออกจากฟุตเตอร์ไปแล้ว —
เจ้าของเว็บรับทราบและเลือกให้อยู่ตลอด)

**หมายเหตุฟุตเตอร์ (การตัดสินใจของผู้เขียน spec)** ตอนคุยกันตกลงว่าจะมีแถบในฟุตเตอร์ด้วย
แต่พอแถบกลายเป็นม่วงทึบแล้ว การมีแถบม่วงอยู่ท้ายทุกหน้าในเว็บทำให้มันกลายเป็นแบนเนอร์ประจำเว็บ
ซึ่งชนกับ anti-goal ข้อ 2 ฟุตเตอร์จึงได้แค่ลิงก์ข้อความ "เลี้ยงกาแฟคุณคูล" ชี้ไป `/support`
วางต่อท้ายรายการลิงก์เดิมใน `components/Footer.tsx` — แย้งได้

**การ์ดประกาศผู้ชนะไม่มีปุ่มนี้** ตรงนั้นฉายขึ้นจอหน้าห้องต่อหน้านักเรียน
สอดคล้องกับ commit `ef5dff3` ที่จงใจทำลิงก์ตรงนั้นให้จาง

## 5. โมชั่น

| จังหวะ | รายละเอียด |
|---|---|
| ตอนเลื่อนมาเจอ | การ์ดเด้งขึ้นมา ย่อจาก 0.93 เป็น 1 พร้อมเลื่อนขึ้น 11px ใน 0.62s · เล่นครั้งเดียว ผ่าน IntersectionObserver threshold 0.35 |
| แก้ว | ลอยขึ้นลง 3px วนรอบละ 3.4s |
| ผิวกาแฟ | กระเพื่อม scale(1.015, .93) วนรอบละ 4.2s ช้ากว่าแก้ว จึงดูเหมือนน้ำจริง |
| ควัน | เส้นขาวสองสายออกจากปากแก้วพร้อมกัน วิ่งขึ้นไปบรรจบกันเป็นรูปหัวใจ แล้วทั้งดวงลอยขึ้น 10px จางหาย · วนรอบละ 4.6s |

ควันทำด้วย `stroke-dasharray` + `stroke-dashoffset` บนสอง path ที่เริ่มจากจุดเดียวกัน
หัวใจจึงถูก **วาดขึ้นมา** ไม่ใช่โผล่มาทั้งดวง ซึ่งเป็นจังหวะที่ทำให้คนหยุดดู

### กฎที่ห้ามละเมิด

1. **`prefers-reduced-motion: reduce` ปิดโมชั่นทั้งหมด** ควันค้างเป็นรูปหัวใจนิ่งๆ แทน
2. **ไม่ขยับระหว่างเกมกำลังเล่น** ถ้าครูยังแข่งเป็ดอยู่ แถบต้องนิ่งสนิท
   เพราะหน้าจอนั้นฉายอยู่หน้าห้อง `DuckRaceApp` รู้สถานะเกมอยู่แล้ว ส่งลงมาเป็น prop
3. **ไม่มีเอฟเฟกต์ Pulse ที่ปุ่ม** ปุ่มที่เต้นเองคือภาษาของป้ายโฆษณา
   ลองทำให้ดูแล้วและตัดทิ้ง ถ้าจะใส่ต้องเป็นการตัดสินใจใหม่ของเจ้าของเว็บ

## 6. ชีท (SupportSheet)

เด้งทับหน้าเดิม ปิดแล้วกลับมาที่เดิมทันที ใช้โครงเดียวกับ `components/AccountSheet.tsx`
(provider + overlay ใน `app/layout.tsx`) เนื้อหาในชีทเรียงจากบนลงล่าง

1. โลโก้ khuncool (`/assets/khuncool-logo.webp`) + หัวเรื่อง "เลี้ยงกาแฟคุณคูล"
   พร้อมบรรทัดรอง "ขอบคุณที่แวะมาช่วยกันครับ"
2. แถบเทาอ่อน "เท่าไหร่ก็ได้ครับ ช่วยให้เว็บอยู่ต่อได้ก็ดีใจแล้ว"
3. QR พร้อมเพย์ + ข้อความ "เปิดแอปธนาคาร สแกน แล้วใส่ยอดที่อยากให้"
4. ช่องฝากข้อความ: ชื่อ (ไม่บังคับ) + ข้อความ
   placeholder: "อยากบอกอะไร หรืออยากให้ทำเครื่องมืออะไรเพิ่ม บอกได้เลยครับ"
5. แถบม่วงอ่อน "อยากได้เครื่องมือหรือสื่อแบบไหนเพิ่ม แจ้งมาได้เลยนะครับ
   **ไม่ต้องโอนก็ส่งมาได้**"
6. ปุ่มส่งข้อความ
7. ตัวอักษรเล็ก สองบรรทัด
   - "ข้อความที่ส่งมาอาจถูกนำไปขึ้นหน้าขอบคุณที่ `/support` ถ้าไม่อยากให้ขึ้นชื่อ
     เว้นช่องชื่อไว้ได้" — **เพิ่มจากผลตรวจ** เดิมไม่มีบรรทัดนี้
     ซึ่งแปลว่าเอาข้อความของครูไปขึ้นเว็บโดยไม่ได้บอกเขาก่อน
   - "เป็นการให้ด้วยความสมัครใจ ไม่ใช่การซื้อสินค้า ไม่มีการคืนเงิน
     และไม่ได้ปลดล็อกอะไรเพิ่มในเว็บ เครื่องมือทุกตัวฟรีเหมือนเดิม"

ข้อ 5 ท่อน "ไม่ต้องโอนก็ส่งมาได้" สำคัญ ถ้าไม่เขียนให้ชัด ครูจะเข้าใจว่าต้องโอนก่อนถึงจะขอได้
ซึ่งทำให้กล่องกลายเป็นการซื้อขาย

**ไม่มีปุ่มเลือกยอด** ตัดสินใจไว้แล้ว เหตุผลคือการให้แบบไทยคุ้นกับ "แล้วแต่กำลังศรัทธา"
มากกว่าเลือกจากเมนูราคา และไม่มีตัวเลขแนะนำด้วย (เคยใส่ "ส่วนใหญ่ช่วยกัน 50 บาท" แล้วเอาออก)

## 7. QR พร้อมเพย์

ใช้ตัวสร้าง QR ที่มีอยู่แล้วใน repo — `lib/qr/qrCode.ts` (byte mode, version 4, ECC L,
รับได้สูงสุด 78 ไบต์) **ไม่ต้องแก้อะไรเลย** ทดสอบแล้วด้วยเลขจริง

| แบบ | ความยาว | ผล |
|---|---:|---|
| ไม่ระบุยอด | 74 ไบต์ | ผ่าน |
| ใส่ยอด 50 บาท | 83 ไบต์ | เกิน |

ซึ่งลงตัวพอดีกับการตัดสินใจไม่ใส่ยอด ถ้าวันหลังอยากใส่ยอด ต้องเพิ่ม alphanumeric mode
ในตัวสร้าง QR ก่อน (payload เป็นตัวเลขกับตัวพิมพ์ใหญ่ล้วน บีบได้แน่นกว่าเกือบเท่าตัว)
ประมาณ 30 บรรทัด — งานคนละก้อน

### โครง payload

```
00 02 01                                    Payload Format Indicator
01 02 11                                    Point of Initiation = static
29 37 0016A000000677010111 01 13 <13 หลัก>  PromptPay, เบอร์แปลงเป็น 0066xxxxxxxxx
58 02 TH
53 03 764                                   THB
63 04 <CRC16-CCITT-FALSE>
```

เขียนเป็น `lib/promptpay.ts` พร้อม unit test (มี vitest อยู่แล้ว) ครอบคลุม
CRC ถูกต้อง · ความยาวไม่เกิน 78 · แปลงเบอร์ 10 หลักเป็น 13 หลักถูกต้อง ·
โยน error ถ้าเลขผิดรูป

### เลขพร้อมเพย์

เบอร์ที่เจ้าของเว็บยืนยันแล้ว และสแกนทดสอบแล้วว่าขึ้นชื่อถูก
เก็บเป็น `NEXT_PUBLIC_PROMPTPAY_ID` — ใส่ค่าจริงใน `.env.local`
และใส่ placeholder ใน `.env.example` ไม่ hardcode ลงโค้ด
(ค่านี้ไม่ลับอยู่แล้วเพราะมันอยู่ใน QR แต่แยกไว้จะเปลี่ยนบัญชีได้โดยไม่ต้องแก้โค้ด)

ถ้าไม่ได้ตั้งค่า env ตัวนี้ ชีทต้องไม่แสดง QR เปล่าๆ ให้ซ่อนส่วน QR
แล้วเหลือแค่ช่องฝากข้อความ

**ที่เจ้าของเว็บรับทราบแล้ว** ครูที่สแกนจะเห็นชื่อจริงของผู้รับในแอปธนาคาร
เลี่ยงไม่ได้ในระบบพร้อมเพย์ และเลขพร้อมเพย์ที่ใช้เป็นเบอร์มือถือ
ซึ่งเท่ากับเผยแพร่เบอร์บนเว็บสาธารณะ (ทางเลือกคือผูกพร้อมเพย์กับเลขบัญชีแทน
เจ้าของเว็บเลือกใช้เบอร์)

## 8. ข้อความจากผู้สนับสนุน

พร้อมเพย์ไม่บอกเว็บว่าใครโอน ข้อความจึงเป็นคนละเรื่องกับการโอนโดยสิ้นเชิง
**ใครก็พิมพ์ได้โดยไม่ต้องโอนจริง** ซึ่งตั้งใจให้เป็นแบบนั้น (ข้อ 6.5)
แต่แปลว่าต้องมีการกลั่นกรองก่อนขึ้นหน้าเว็บ

### ตาราง

```sql
create table public.kc_support_messages (
  id         bigint generated always as identity primary key,
  name       text,
  message    text not null,
  status     text not null default 'pending',
  created_at timestamptz not null default now()
);

alter table public.kc_support_messages enable row level security;

alter table public.kc_support_messages
  add constraint kc_support_messages_name_length
    check (name is null or char_length(name) between 1 and 60),
  add constraint kc_support_messages_message_length
    check (char_length(message) between 1 and 500),
  add constraint kc_support_messages_status_known
    check (status in ('pending', 'approved', 'hidden'));

-- anon และ authenticated ไม่มีสิทธิ์อะไรกับตารางนี้เลย
-- การเขียนผ่าน API route ที่ใช้ service-role key การอ่านทำฝั่ง server
revoke all on table public.kc_support_messages from anon, authenticated;
grant select, insert, update on table public.kc_support_messages to service_role;
```

ต่างจากแพตเทิร์นของ `tool_events` ที่เปิดให้ anon insert ตรงๆ โดยตั้งใจ
คอมเมนต์ใน `supabase/migrations/20261104150000_tighten_tool_events_insert.sql`
เขียนไว้เองว่าแพตเทิร์นนั้นไม่มีการจำกัดอัตรา ใครก็ยิงรัวได้ ซึ่งกับตัวเลขสถิติไม่เป็นไร
แต่กับข้อความที่จะขึ้นหน้าเว็บคนละเรื่อง จึงดันทุกอย่างไปอยู่หลัง API route แทน

### API route

`POST /api/support/message` — รับ `{ name?, message }`
ตรวจความยาว ตัดช่องว่างหัวท้าย ปฏิเสธข้อความว่าง เขียนด้วย service-role key
ตอบ 200 เสมอเมื่อสำเร็จ ไม่คืนข้อมูลอะไรกลับ

**การจำกัดอัตรายังไม่ตัดสินใจ — ดูข้อ 12**

### การกลั่นกรอง

แท็บใหม่ในหน้าแอดมิน (`app/admin/tabsConfig.tsx` + `app/admin/tabs/SupportTab.tsx`)
แสดงข้อความที่ `status = 'pending'` พร้อมปุ่ม **อนุมัติ · ซ่อน · ลบถาวร**
ใช้ `requireAdmin` + `createServiceRoleClient` เหมือนแท็บอื่น

ปุ่มลบถาวรเพิ่มจากผลตรวจ ถ้าครูเขียนมาแล้วขอให้ลบ ต้องมีทางลบจริง
ไม่ใช่แค่ซ่อน

**หมายเหตุสำหรับคนเขียนโค้ด (จากผลตรวจ)** ทุก route ใน `app/api/admin/*`
ตอนนี้เป็น GET ล้วน และ `app/admin/useAdminFetch.ts` ก็ทำแต่ GET
การอนุมัติ/ซ่อน/ลบ เป็น **การเขียนครั้งแรกของฝั่งแอดมินในโปรเจกต์นี้**
จึงต้องเขียนทางเรียก API ของตัวเองเพิ่ม ไม่ใช่ลอกแท็บเดิมมาได้ทั้งดุ้น

### กำแพงขอบคุณ

อยู่ในหน้า `/support` เท่านั้น ไม่อยู่ในชีท (ชีทต้องสั้น)
เป็น server component อ่านเฉพาะ `status = 'approved'` ด้วย service-role key
เรียงใหม่ก่อน จำกัด 30 รายการ
ข้อความที่ไม่ได้ใส่ชื่อ แสดงเป็น "ไม่ประสงค์ออกนาม"

### รู้ได้ยังไงว่ามันเวิร์ก

พร้อมเพย์ไม่บอกเว็บว่ามีคนโอน เป้าหมายในข้อ 1 จึงวัดตรงๆ ไม่ได้
สิ่งที่วัดได้คือมีคนเห็นแถบกี่ครั้ง และเปิดชีทกี่ครั้ง ซึ่งพอบอกได้ว่า
แถบทำงานไหม และคนเปิดชีทแล้วเงียบหรือเปล่า

ใช้ `lib/trackToolEvent.ts` ที่มีอยู่แล้ว

- แถบเข้ามาในจอ → `trackToolEvent("support-strip", "view")`
- เปิดชีท → `trackToolEvent("support-sheet", "use")`

ใช้ค่า `view` กับ `use` ที่ constraint ของ `tool_events` อนุญาตอยู่แล้ว
จึง **ไม่ต้องเขียน migration เพิ่ม** (constraint คือ `event in ('use','view')`
จาก `20261104150000_tighten_tool_events_insert.sql`)

และแท็บภาพรวมของแอดมินให้โชว์จำนวนข้อความที่ยังรออนุมัติ
จะได้ไม่ต้องจำว่าต้องเข้าไปเปิดแท็บดูเอง

## 12. ยังต้องให้เจ้าของเว็บตัดสินใจ

**จะจำกัดอัตราการส่งข้อความด้วยวิธีไหน** สองทาง

- **เก็บ IP แบบแฮช** แฮช IP รวมกับ salt ที่เปลี่ยนทุกวัน เก็บไว้ 24 ชั่วโมงแล้วลบ
  ปฏิเสธถ้าส่งเกิน 3 ข้อความใน 1 ชั่วโมงจาก IP เดียวกัน · กันสแปมได้จริง
  แต่เป็นการเก็บข้อมูลที่โยงกลับไปหาผู้ใช้ได้ในระยะสั้น ต้องเขียนในนโยบายความเป็นส่วนตัว
- **จำกัดจำนวนคิวรวม** ไม่เก็บอะไรเกี่ยวกับผู้ใช้เลย ถ้ามีข้อความ `pending` เกิน 20 รายการ
  ปิดรับชั่วคราวจนกว่าจะกลั่นกรองหมด · ไม่แตะข้อมูลส่วนบุคคล
  แต่คนยิงรัวทำให้คิวเต็มแล้วครูจริงส่งไม่ได้

ทางแรกกันสแปมได้ดีกว่า ทางที่สองสะอาดกว่าเรื่องข้อมูลส่วนบุคคล
เว็บนี้มีผู้ใช้จาก Google ราว 500 คนต่อเดือน โอกาสโดนสแปมจริงจังต่ำ
ผู้เขียน spec เอนไปทางที่สอง แต่เป็นการตัดสินใจของเจ้าของเว็บ
