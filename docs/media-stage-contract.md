# กติกาการทำ responsive ของสื่อ /media

ทุกเกมใน `/media` ต้องทำตาม 4 ข้อนี้ ระบบกลางอยู่ที่ [`app/media/_stage/`](../app/media/_stage/)

---

## 1. ตัวเกมห้ามรู้จัก viewport

**ห้าม** ใช้ `vw`, `vh`, `dvh`, `window.innerWidth`, `matchMedia` ในโค้ดหรือ CSS ของตัวเกม

**ให้ใช้** `cqi` (ตามความกว้างเวที), `cqb` (ตามความสูงเวที), `%`, และ token จากข้อ 3

เหตุผล: เกมตัวเดียวกันต้องแสดงผลถูกต้องทั้งตอนอยู่ในคอลัมน์หน้าเว็บ ตอนเต็มจอ และตอนถูกฝังใน embed — ทั้งสามกรณีมี viewport เท่ากันแต่เวทีคนละขนาด

มีที่เดียวที่อ่าน viewport ได้คือ `.kc-stage` ใน `stage.css` เพราะการตัดสินว่าจะให้เกม "ได้พื้นที่เท่าไร" เป็นเรื่องของหน้าเว็บ ไม่ใช่ของเกม

## 2. โครงสร้าง 2 ชั้น

```tsx
const { stageProps, isFull, toggle } = useStage<HTMLDivElement>();

<div {...stageProps} className="kc-stage">
  <div className={`kc-stage-body ${styles.lab}`}>
    …เกม…
  </div>
</div>
```

- `.kc-stage` — กำหนดขนาดเวที เป็น container (`container: kcstage / size`) และเป็นตัวที่เข้าเต็มจอ
- `.kc-stage-body` — ถือ token และเป็นตัวที่ container query เข้าถึงได้

⚠️ **ห้ามตั้ง `position` หรือ `overflow` แบบ inline บน `.kc-stage-body`** — มันเป็นของ `stage.css` (`position:absolute; inset:0`) ถ้าเขียน inline ทับ body จะหลุดออกมาอยู่ใน flow แล้วโตเกินเวทีได้ โดยที่ทุกอย่างยัง "ดูปกติ" · สคริปต์ตรวจมีช่อง `bodyUnbound` ไว้จับข้อนี้

ต้องมี 2 ชั้นเพราะ container query แต่งได้เฉพาะ**ลูก**ของ container ไม่ใช่ตัว container เอง

## 3. ใช้ token ตาม "ทรง" ไม่ใช่ตามชนิดอุปกรณ์

`stage.css` ให้ token 3 ชุดตามรูปทรงของเวที ณ ขณะนั้น

| ทรง | เงื่อนไข | เกิดขึ้นเมื่อ |
|---|---|---|
| **wide** (ค่าตั้งต้น) | อื่นๆ ทั้งหมด | เดสก์ท็อป, โปรเจกเตอร์, แท็บเล็ตแนวนอน |
| **portrait** | `aspect-ratio < 0.9` | มือถือแนวตั้ง, เต็มจอแนวตั้ง |
| **short** | `aspect-ratio >= 0.9` และ `height < 440px` | มือถือแนวนอน, หน้าต่างเตี้ย |

Token ที่มี: `--kc-tap`, `--kc-pad`, `--kc-gap`, `--kc-radius`, `--kc-fs-display`, `--kc-fs-title`, `--kc-fs-head`, `--kc-fs-body`, `--kc-fs-label`

ขนาดตัวอักษรทุกตัวเป็น `max(พื้น, สัมพัทธ์)` เพราะเวทีอาจ "ทรงกว้างแต่เล็ก" ได้ (มือถือแนวนอน, แท็บเล็ตแนวตั้ง) ถ้าใช้สัมพัทธ์ล้วนตัวอักษรจะเหลือ 9px

ปุ่มที่ใส่ `className="kc-tap"` จะได้ `min-width`/`min-height` เท่า `--kc-tap` อัตโนมัติ (40px ทรงกว้าง, 44px ทรงเตี้ย, 48px ทรงตั้ง)

## 4. เต็มจอ = ขยายเวที ไม่ใช่ย่อ–ขยายภาพ

ใช้ `useStage()` เท่านั้น ห้ามเขียน `requestFullscreen` เอง ห้ามใช้ `transform: scale()` เพื่อให้พอดีจอ

`useStage` ใส่ `data-fullscreen` ให้ `.kc-stage` ทั้งกรณี native fullscreen และกรณี fallback (iOS Safari ไม่มี Fullscreen API สำหรับ `<div>`) เวทีจึงกลายเป็น `100vw × 100dvh` แล้วทุกอย่างข้างในคำนวณใหม่เองจาก container query

ผลพลอยได้: **การหมุนจอขณะเต็มจอทำงานเองโดยไม่ต้องเขียนโค้ดเพิ่ม** เพราะไม่มีค่าขนาดไหนถูกจำไว้ตั้งแต่ตอนกดเต็มจอ

### `contentHiddenBehindScroll` — ช่องที่ต้องอ่าน ไม่ใช่แค่ดู pass

เกณฑ์ข้อแรก ("เลื่อนไปหาไม่ได้") ผ่านทันทีถ้ามีอะไรเลื่อนไปถึงได้ ซึ่งตอบคำถามว่า *เข้าถึงได้ไหม* แต่ไม่ได้ตอบว่า *ผู้เล่นจะรู้ไหมว่ามีอยู่*

เคสจริง: Phonics Bingo บนมือถือแนวตั้งเคยขึ้น `pass: true` ทั้งที่แสดงการ์ด 12 จาก 16 ใบ เพราะกริดมี scrollbar ของตัวเอง การ์ดที่ถูกซ่อนเลยนับว่า "เข้าถึงได้" ครบ — กล่องเล็กที่เลื่อนอยู่ในจอแทบไม่มีสัญญาณบอก เด็กเห็นสี่แถวแรกก็เล่นต่อโดยไม่รู้ว่ายังมีอีก

**ไม่ใช่เกณฑ์ตก** เพราะบางที่เลื่อนถูกแล้ว (รายการผลลัพธ์ที่มี 1 แถวต่อ 1 ข้อ ไม่มีทางกำหนดความสูงตายตัวได้) สิ่งที่ตัดสินคือ**อะไรถูกซ่อน** สคริปต์จึงรายงานตัวนั้น:

| ค่าที่ได้ | แปลว่า |
|---|---|
| `hiddenControls: 0` | ไม่ถูกรายงาน — ไม่มีปุ่มหาย |
| ซ่อนปุ่มตัวเลือก / การ์ดคำตอบ | **ต้องแก้ layout** ผู้เล่นเห็นตัวเลือกไม่ครบ |
| ซ่อนท้ายย่อหน้า / รายการยาวที่ไม่มีขอบเขต | ปล่อยได้ |

ดูช่อง `sample` ประกอบว่าปุ่มที่หายคืออะไร

## 5. หน้า intro ต้องยุบได้ ไม่ใช่แค่หน้าเล่น

หน้าเล่นมักถูกออกแบบให้ยืดหยุ่นอยู่แล้ว แต่**หน้า intro/setup มักไม่ถูกคิดถึง** — มันวางกอง
โลโก้ + หัวข้อ + คำอธิบาย + การ์ดตัวเลือก + ปุ่มเริ่ม เรียงลงมาเฉยๆ ซึ่งพังทันทีบนเวทีเตี้ย

จากการตรวจทั้ง 16 เกม: **18 จาก 23 เกณฑ์ตกเป็นเรื่องเดียวกันหมด** — ปุ่มที่พาไปหน้าถัดไป
ตกอยู่นอกเวทีและเลื่อนไปหาไม่ได้ ผู้เล่นติดอยู่หน้าแรก เข้าเกมไม่ได้เลย

ทั้ง 4 เกมที่แก้ (classroom-objects, is-are-sorting, coding-maze, science-lab-crisis)
มีต้นเหตุเดียวกัน: **ทุกอย่างถูกกำหนดขนาดจาก `cqi` (ความกว้างเวที) ทั้งที่สิ่งที่หมดคือความสูง**
เวที 780×304 กว้างพอให้ทุก `clamp()` ชนค่าสูงสุด แต่สูงไม่พอสักอย่าง

### 4 ขั้น เรียงจากถูกไปแพง — หยุดเมื่อพอดีแล้ว

วัดก่อนว่าขาดกี่ px แล้วไล่จากขั้นที่เสียข้อมูลน้อยที่สุด

| ขั้น | ทำอะไร | ต้นทุน |
|---|---|---|
| 1 | **ยุบ margin/padding เป็น px คงที่** — margin หน่วย `cqi`/`%` โตขึ้นพอดีตอนที่เหลือน้อยที่สุด | ไม่เสียอะไร |
| 2 | **วัดขนาดด้วย `cqb` ไม่ใช่ `cqi`** เพราะความสูงคืองบ | ไม่เสียอะไร |
| 3 | **ให้ intro กินพื้นที่ที่เหลือแล้วจัดกึ่งกลาง** — `flex:1 1 auto` + `justify-content: safe center` | ไม่เสียอะไร |
| 4 | **ตัดของที่ไม่มีหน้าที่ในทรงนี้** — ภาพตกแต่ง แล้วค่อยย่อหน้าคำอธิบาย | เสียข้อมูล |

science-lab-crisis ขาด 16px → ขั้น 1 พอแล้ว ไม่ต้องตัดอะไร
classroom-objects ขาด 180px → ต้องถึงขั้น 4 (478px → 205px)

**ห้ามแก้ด้วย `overflow:auto`** — นั่นคือย้ายปุ่มเริ่มไปซ่อนหลัง scroll ซึ่งคือสิ่งที่
`contentHiddenBehindScroll` ถูกเพิ่มมาจับพอดี

### `safe center` ไม่ใช่ `center` เฉยๆ

ถ้าเนื้อหาสูงเกินกล่อง `justify-content:center` จะดันส่วนเกิน**ออกทั้งสองด้าน** และครึ่งบน
ไปอยู่เหนือเวทีซึ่งไม่มีทางเลื่อนไปถึง — coding-maze เคยมี level badge ลอยอยู่เหนือเวที 60px
โดยไม่มีใครเห็น ส่วน `safe` จะถอยไปเป็น `flex-start` ให้ส่วนเกินไปกองข้างล่างที่ยังพอเห็นได้

### แนวนอนกับแนวตั้งแก้คนละแบบ

**ห้ามใช้กฎเดียวครอบทั้งสองทรง** เพราะขาดคนละอย่าง

| ทรง | ขาดอะไร | ทำอะไร |
|---|---|---|
| **short** (มือถือแนวนอน, แท็บเล็ตแนวตั้ง) | ความสูง — กว้างเหลือเฟือ | ตัดเนื้อหาออก (ขั้น 4) |
| **portrait** (มือถือแนวตั้ง) | ความกว้าง — ข้อความห่อหลายบรรทัดจนดันปุ่มตก | แค่บีบระยะห่างแนวตั้ง เก็บของครบ |

classroom-objects ตกทั้งสองทรงแต่คนละเหตุ — แนวนอนต้องตัดการ์ดกับคำอธิบายทิ้ง
ส่วนแนวตั้งแค่ลด margin ก็พอ การ์ดกับคำอธิบายยังอยู่ครบ

### ⚠️ กับดัก: เวทีเตี้ยก็เป็นเวทีกว้างด้วย

`aspect-ratio >= 0.9` กับ `height < 440px` **ไม่ใช่ทางเลือกที่แยกจากกัน** — มือถือแนวนอนเข้าเงื่อนไขทั้งคู่
กฎในบล็อก wide จึงยังบังคับใช้อยู่ และกฎในบล็อก short ต้อง**ชนะ**มัน ไม่ใช่แค่เขียนทับ

เจอปัญหานี้ 2 ครั้งติดจาก 4 เกม:

- **coding-maze** — กฎ shape อยู่ใน `<style jsx>` ซึ่ง styled-jsx เติม class ของตัวเองให้ทุก selector
  กฎใน CSS module จึงแพ้ specificity เสมอ ต้องย้ายไปเขียนใน styled-jsx และวาง**หลัง**บล็อก wide
- **science-lab-crisis** — บล็อก wide ใช้ `.intro > p:not(.kicker)` แต่บล็อก short เขียนแค่ `.intro > p`
  ซึ่ง specificity ต่ำกว่า กฎเลยไม่มีผล ทั้งที่ค่าที่เขียนไว้ถูกหมดแล้ว

**อาการ:** แก้ CSS แล้วตัวเลขไม่ขยับเลย — ให้สงสัยเรื่อง specificity ก่อนสงสัยค่าที่เขียน
เช็คด้วยการอ่าน computed style จริงว่าค่าที่ได้มาจากกฎไหน

### ขนาดตัวอักษรใช้ `clamp(พื้น, สัมพัทธ์, เพดาน)`

`min(14px, 4.6cqb)` **ไม่มีพื้น** — มันแค่กันไม่ให้ใหญ่เกิน แต่เล็กได้ไม่จำกัด
coding-maze เคยหลุดไป 10.95px แล้วตกเกณฑ์ 11px ด้วยเหตุนี้
ใช้ `clamp()` หรือ `max(พื้น, สัมพัทธ์)` แบบเดียวกับ token ใน `stage.css`

ผิดซ้ำ 3 รอบในสัปดาห์เดียว รวมถึงเขียน `9px` / `10px` เป็นพื้นตรงๆ ใน density-lab
กับ motion-lab เวลาแตะ font-size ในบล็อก short **ให้ไล่เช็คทุกค่าในบล็อกนั้น** ไม่ใช่แค่ค่าที่เพิ่งแก้

### ⚠️ ทรง wide ก็เตี้ยได้ — บางเคสต้องวัดความสูงเป็น px

เวที `960×540` (แท็บเล็ตแนวนอน ในหน้า) กับ `1096×617` (เดสก์ท็อป ในหน้า) เป็น **16:9 เท่ากันเป๊ะ**
container query ที่อ่านแต่ aspect-ratio จึงแยกสองอันนี้ไม่ออก ทั้งที่อันหนึ่งพัง อีกอันไม่พัง
สิ่งที่ต่างคือความสูงจริงเป็น px

motion-lab กับ typing-defense ต้องใช้ `@container kcstage (aspect-ratio >= 0.9) and (height < 580px)`
ด้วยเหตุนี้ — 580px กันเดสก์ท็อป 617px ไว้ ครอบ 540px ลงมา

ถือเป็นการเบี่ยงจาก 3 ทรงมาตรฐาน ใช้เมื่อจำเป็นจริงและ**เขียนเหตุผลกำกับไว้ในไฟล์**

### ⚠️ เกมที่สุ่มเนื้อหา ต้องแก้ให้ทนตัวเลือกที่ยาวที่สุด

motion-lab สุ่มโจทย์ 4 จาก 6 ข้อทุกครั้งที่โหลด ตัวเลือกส่วนใหญ่เป็นตัวเลขสั้นๆ (`"18 วินาที"` 9 ตัวอักษร)
แต่มีข้อหนึ่งที่ตัวเลือกเป็นประโยคเต็ม **63 ตัวอักษร** — ยาวกว่า 7 เท่า

ผลคือเกมเดียวกันอาจผ่านรอบนี้แล้วพังรอบหน้า ขึ้นกับว่าเด็กสุ่มได้ชุดไหน

`scripts/audit-games.mjs` seed `Math.random` ไว้ **และเลือก seed ที่ให้ชุดยาวที่สุด** (ปัจจุบันคือ 15)
เพื่อให้ค่าตั้งต้นวัดเคสหนัก ไม่ใช่เคสที่โชคดี ถ้า pool คำถามเปลี่ยน ต้องรัน sweep หา seed ใหม่

```bash
node scripts/audit-games.mjs --seeds=15,17,24,1,6,39 motion-lab
```

sweep แล้วเก็บผลแย่สุดต่อช่อง — แก้เสร็จต้องผ่านทุก seed ไม่ใช่แค่ seed เดียว

**ความยาวข้อความก็ต้องบังคับเหมือนกัน** — seed คุมว่า *หยิบอันไหน* แต่ไม่คุมว่า *ยาวแค่ไหน*
vocabulary-arcade มีคำตั้งแต่ `"bee"` (3) ถึง `"triangle ruler"` (14) ค่ากลางประมาณ 5
`audit-games.mjs` จึงมีช่อง `stress` ต่อเกม ใส่ selector กับคำที่ยาวที่สุดที่เกมนั้นสร้างได้
แล้ววัดซ้ำอีกรอบด้วยคำนั้น เก็บผลที่แย่กว่า

> **เวลาเพิ่ม `stress` ให้เกมใหม่ ต้องพิสูจน์ว่ามันทำงานจริง**
> ถ้าใส่คำยาวสุดแล้วผลไม่แย่ลงเลย อาจแปลว่า layout ทนจริง **หรือ selector ไม่ตรงแล้วไม่ได้ทำอะไรเลย**
> แยกสองอย่างนี้ด้วยการลองใส่คำยาวเกินจริงชั่วคราว — ถ้าผลไม่เปลี่ยน แปลว่า selector พัง

## 6. ⚠️ เครื่องมือวัดต้องคืนสภาพก่อนวัด

เจอ artifact ของ harness มาแล้ว **3 ครั้ง** รูปแบบเดียวกันทุกครั้ง:
**harness แหย่หน้าเว็บเพื่อสั่งงาน แล้ววัดโดยไม่คืนสภาพก่อน** ผลที่ได้จึงเป็นเรื่องของเครื่องมือ ไม่ใช่ของเกม

| # | ทิ้ง state อะไรไว้ | อ่านออกมาเป็น | เสียเวลาไปกับ |
|---|---|---|---|
| 1 | **scroll ค้าง** — Playwright เลื่อน container เพื่อกดปุ่มที่อยู่นอกจอ แล้ว offset ค้างข้ามหน้า | 4 เกม "หน้าเล่นพังจนเหลือพื้นหลังเปล่า" | รายงานผิดทั้งรอบ ต้องแก้แล้วตรวจใหม่ |
| 2 | **`Math.random` ไม่ได้ seed** | ผลขยับเองระหว่างรอบโดยไม่มีใครแก้โค้ด (72 → 73) | เทียบผลข้ามรอบไม่ได้เลย |
| 3 | **hover ค้าง** — เมาส์ค้างตรงที่เพิ่งคลิก โดนปุ่มที่ `scale(1.06)` ตอน hover | 4 ช่อง "การ์ดล้นขอบ 1–12px" ทั้งที่ความสูงจริงพอดี | ไล่หาบั๊กที่ไม่มีอยู่จริง |

### เช็คลิสต์ก่อนวัดทุกครั้ง

```js
await page.mouse.move(0, 0);        // 3 — เอาเมาส์ออกจาก stage
await page.waitForTimeout(250);     //     รอ transition ของ :hover คลาย (0.18s)
document.querySelectorAll("*").forEach(el => { el.scrollTop = 0; el.scrollLeft = 0 });  // 1
// 2 — seed Math.random ตั้งแต่ addInitScript ก่อน script ของหน้าเว็บรัน
```

**อาการที่ควรสงสัย artifact ก่อนสงสัยเกม:**
- ผลต่างกันระหว่างรอบทั้งที่ไม่ได้แก้โค้ด
- `getBoundingClientRect()` ไม่ตรงกับ `offsetHeight` → มี `transform` อยู่ (hover/animation)
- ล้นแค่ไม่กี่ px เฉพาะบางขนาดจอ เฉพาะโหมดเต็มจอ
- แก้ CSS แล้วตัวเลขไม่ขยับเลย → specificity (ดูข้อ 5) หรือวัดผิดตำแหน่ง

**ถ้าเจอตัวที่ 4** ให้ถามก่อนว่า *harness ทำอะไรกับหน้าเว็บไปบ้างก่อนถึงจุดที่วัด* แล้วคืนสภาพนั้นให้หมด
วิธียืนยันว่าเป็น artifact: วัดค่าเดิมซ้ำหลังคืนสภาพ ถ้าค่าเปลี่ยน แปลว่าเป็นของเครื่องมือ

## 7. วัด chrome รอบๆ ก่อนแตะของที่เสี่ยง

เวลาหน้าจอหนึ่งล้น สัญชาตญาณคือไปแก้ "ของใหญ่" ตรงกลาง — ย่อภาพ ลดพิกัด เปลี่ยน artwork
**ผิดลำดับ** ให้วัดสิ่งที่อยู่รอบๆ ก่อนเสมอ เพราะหลายครั้งพื้นที่ที่หายไปไม่ได้อยู่ที่เนื้อหา

เคสจริง — plant-tree ของ family-tree มีแผนจะลด row pitch ของต้นไม้ (cy 6/156/306 → 6/136/266)
ซึ่งแปลว่าต้องไล่แก้เส้น SVG ที่เขียนพิกัดมือทุกเส้น (`M390 58 V112`, `M100 112 H660`)
เป็นการแก้ที่เสี่ยงที่สุดในโปรเจกต์นี้ และถ้าผิดจะเห็นได้ทางภาพอย่างเดียว

พอวัด chrome ก่อน พบว่า**ไม่ต้องแตะพิกัดเลยสักเส้น** ของจริงอยู่ที่:

| ที่มา | ได้คืน |
|---|---|
| บอร์ดไม่ย่อเลย เพราะ `max-height:100%` วัดจากความสูงหน้าจอทั้งหมด ไม่ใช่ที่เหลือ | scale 0.96 → 0.25 |
| `padding-bottom: clamp(20px,6cqb,100px)` — ที่ว่างเปล่าใต้คลังคำ | ถึง 100px |
| แถวคำใบ้ "ลากการ์ดจากด้านล่าง…" ซึ่งเคอร์เซอร์กับช่องประซ้อนบอกอยู่แล้ว | 21px |
| การ์ดมาสคอต + margin | ~50px |
| `min-height:44px` ของแถบคลังคำ | ~40px |

### ลำดับที่ควรไล่

1. **ตัวที่ไม่ยอมย่อ** — element ที่ควรยืดหยุ่นแต่ไม่ยืดหยุ่น (`flex:0 1 auto` ที่ยุบไม่ได้/โตไม่ได้, `max-height:100%` ที่วัดผิดกล่อง) มักให้ผลมากที่สุดและไม่เสียอะไรเลย
2. **margin/padding/gap** — โดยเฉพาะที่เขียนด้วย `cqi`/`%` ซึ่งโตขึ้นพอดีตอนที่เหลือน้อยที่สุด
3. **chrome ที่อธิบายสิ่งที่ UI บอกอยู่แล้ว** — คำใบ้ ป้ายกำกับ หัวข้อซ้ำ
4. **แล้วค่อย** ถึงเนื้อหา พิกัด หรือ artwork

### เกณฑ์ตัดสินว่าพอหรือยัง

**"พอดี" ไม่ใช่เกณฑ์** — matching เคยพอดีทุกสถานะกลางทางแต่ยังตก: scale 0.25 ปุ่ม 14px, scale 0.40 ปุ่ม 22px
ต้องเช็ค **เป้าแตะ ≥ 24px** และ **ตัวอักษร ≥ 11px** ควบคู่ไปด้วยเสมอ ไม่ใช่แค่ `scroll === client`
